# CPLayout Agent Known Gaps

This file tracks gaps in the agent/skill process layer. It does not replace product validation checklists.

| Gap | Impact | Current mitigation |
| --- | --- | --- |
| Custom agent runtime spawning was exercised in the 2026-06-02 plan-consolidation pass, but fresh-session hook-injected routing remains unverified after merge. | Subagents returned useful read-only findings in this session, but automatic route-to-agent behavior depends on the active runtime, trusted project config, and available multi-agent tools. | Keep agents read-only by default; in the next fresh session verify prompt-triage context and record either spawned specialists or `Accepted fallback:`. |
| Persistent subagent authorization is now documented, but local hooks cannot guarantee execution by themselves. | The owner preference is durable in `AGENTS.md`, skill references, and prompt registry, yet a coordinator could still ignore advisory context in an unmanaged session. | Use managed `requirements.toml`, managed hooks, and reviewer discipline for stronger process adherence; continue to require explicit subagent decision summaries. |
| Hook scripts are validated directly, but true in-session injection still requires a fresh Codex session after merge. | The `UserPromptSubmit`, `SubagentStart`, `PreToolUse`, and `Stop` scripts return valid sample output where expected, but active injection depends on trusted project config and runtime hook loading. | Start a fresh Codex session on the merged branch and prompt `Use Google Earth imagery and SQLite to improve center pivot UI`; verify injected context mentions only the top ranked specialists and CPLayout boundaries. |
| Managed hook enforcement is documented but not endpoint-verified here. | The example `requirements.toml` can parse locally, but non-bypass behavior depends on managed requirements deployment, copied scripts under the managed directory, Codex restart, and `/hooks` verification on the target machine. | Use `docs/codex-managed-hook-deployment.md`; after deployment, verify startup config, managed hook trust status, and sample prompts in a fresh Codex session. |
| Managed prompt triage depends on route data availability when scripts run outside the repo. | A managed script copied to an administrator directory can find route data from the current CPLayout checkout or adjacent managed files, but neither path is endpoint-proven. | Copy `.codex/hooks/cplayout_route_data.json` with managed scripts or run Codex from the CPLayout checkout; verify a matched prompt emits expected route ids. |
| Hook guardrails are not full command enforcement. | Local `PreToolUse` can deny narrow destructive commands, but broader policy still depends on model behavior and managed deployment. | Use managed requirements `[rules].prefix_rules` for hard command prompt/forbid policy if stronger enforcement is required. |
| Stop-hook continuation behavior remains advisory until live managed runtime proof exists. | Current official docs expose `Stop` as a hook event and `additionalContext` as hook output, but this pass did not prove a Stop hook can force continuation in a live managed session. | Treat `cplayout_stop_multi_agent.py` as a managed-policy advisory that makes missing subagent decisions visible; record live continuation evidence before claiming hard enforcement. |
| Prompt triage is weighted keyword scoring. | Broad or unusual prompts may miss a relevant specialist or rank specialists imperfectly. | Route data caps output at 3 specialists and keeps broad terms low weight; the coordinator still owns final routing using `AGENTS.md`, repo evidence, and source-backed judgment. |
| Source ledger is a seed, not a complete research knowledge base. | Center-pivot design, UI, database, and imagery methods still need task-specific source review. | Require source-backed updates for each new claim and keep unknowns explicit. |
| Process records can lag product code after implementation passes. | Earlier process-only updates did not change runtime code, but later passes may add storage, UI, or companion behavior that needs record updates. | Keep this file, the focused plan, and source ledger synchronized after product changes; do not use older process-only statements as current product status. |
| No first-class ML/CV pivot-center locator loop existed before the 2026-06-01 loop document. | Existing browser mapping loop and boundary-focused ML reports cannot prove automatic center-pivot locating quality. | Use `docs/ml-cv-pivot-locating-improvement-loop.md` and `npm run verify:ml-cv-loop` as the pivot-locator control loop until executed evidence rows replace planned rows. |
| Local companion pivot detection and real-fixture manifest ingestion exist, but real-world projected-XY pivot proof remains blocked. | Image-space Hough circle detections may identify crop rings or overlays, and `build-evidence-packet --real-pivot-fixtures` can accept calibrated truth labels, but no operator-supplied real fixture set has been proved. | Use `detect-pivot-candidates` for advisory image evidence; use `cplayout-real-pivot-fixtures-v1` only with operator-approved truth, project-CRS calibration, matching hashes, and Review Apply XY gates. |
| Pivot-locator fixture evidence is not yet curated as durable checked-in summaries. | Ignored local reports may be useful but cannot serve as durable project knowledge or regression proof. | Create milestone summaries under `docs/evidence/continuous-improvement/ml-cv-pivot-locating-*` with artifact hashes and validation results. |
| Google Earth render proof exists for the documented 2026-05-30 local proof packet, but it is not a native/mobile or general runtime claim. | The proof manifest and screenshot show one passed local Google Earth Pro visual-fidelity run; it does not prove future KML/KMZ files, CPLayout native runtime behavior, or automatic geometry correctness. | Require non-black rendered evidence and cleanup status for each new Google Earth visual-fidelity claim. |
| Project ZIP adjacent review data is browser/local-proven, but native review-data persistence and sharing remain unverified. | Project-store and Playwright prove archive parsing/export/import for web local storage; they do not prove Android/iOS file picker/share behavior or Expo SQLite review-data tables on device. | Use `docs/android-native-verification.md`, `npm run check:android-tools`, and a completed device/emulator report before making native ZIP or SQLite review-data claims. |
| Roadmap completion now has a single automation runner, but external resources still have to be present. | `npm run verify:roadmap` can run local gates and classify missing proof as blocked without asking for step-by-step decisions; it cannot create an adb device, calibrated fixture, native MapLibre screenshot, or qualified field-review evidence. | Provide durable inputs at the default paths or environment variables consumed by `tools/roadmapCompletion.ts`; future agents should run the runner before asking for operator direction. |
| Native Android/iOS persistence, ZIP sharing, and native map rendering remain unverified here. | The agent process must not report production-ready native behavior from compile or config checks alone. | Use `docs/android-native-verification.md` and platform-specific checklists before making runtime claims. |
| Native/on-device ML for pivot locating remains unverified. | ONNX Runtime React Native and mobile deployment remain candidate technology only; Expo Go cannot prove arbitrary native-library behavior. | Keep ML/CV pivot locating in the local companion until an Expo development build proves model load, inference, latency, memory, power, network isolation, and parity on Android and iOS. |
| Whole-codebase 100-iteration loop includes blocked evidence outcomes. | `docs/whole-codebase-improvement-loop-2026-06-01.md` is batch-classified through row 100, but rows marked `Blocked` are unresolved proof or implementation gaps rather than pass claims. | Use `npm run verify:whole-loop` to enforce row continuity and evidence requirements; do not promote blocked rows until their own proof gates pass. |
| Whole-codebase loop verification cannot prove native, Google Earth, real-world ML/CV, or browser runtime behavior by itself. | The verifier checks ledger structure and passed-row evidence fields, not external devices, visual render state, or real-world fixture truth. | Keep each proof class behind its own validation gate and checklist. |
| Whole-codebase loop rows 011-100 are batch-classified rather than individually hand-implemented feature changes. | The loop records research, classification, validation, and blockers across the codebase, but some rows deliberately stop at documented evidence or blocker inventory. | Treat batch evidence as risk inventory; use each blocked row as the next targeted implementation slice before claiming product behavior. |
